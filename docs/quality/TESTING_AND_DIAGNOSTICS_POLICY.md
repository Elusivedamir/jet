# Регламент диагностики и тестирования Jetson Messenger

**Статус:** [СОГЛАСОВАНО ЗАКАЗЧИКОМ — 2026-11-23]  
**Область:** весь проект; для PoC JuggleIM применяется немедленно.  
**Цель:** быстро локализовать дефект, не тратить время на повторные полные E2E-прогоны и не объявлять исправление успешным без проверяемых доказательств.

## 1. Базовый принцип

Проверяем систему снизу вверх — от самого узкого слоя к пользовательскому сценарию. При отказе останавливаемся на первом неподтверждённом слое, сохраняем диагностику и исправляем только установленную причину. Не меняем одновременно несколько независимых компонентов без доказанной необходимости.

## 2. Обязательная последовательность проверок

Для сетевого подключения и доставки сообщений:

1. **Конфигурация и окружение:** адреса, порты, DNS/маршрутизация, доступность сервиса, переменные окружения, версии SDK и сервера.
2. **Транспорт TCP:** соединение с нужным host:port.
3. **TLS:** handshake, цепочка сертификатов, SAN/hostname/IP, срок действия и доверие Android-приложения.
4. **HTTP WebSocket Upgrade:** правильный путь и заголовки; ожидаемый статус 101 Switching Protocols. Ответ 200 не считается успешным WebSocket Upgrade.
5. **Протокол и SDK:** корректность фреймов, endpoint, версии SDK, обязательных параметров подключения и callback-состояний.
6. **Авторизация:** токен, app key/sign key, подпись, идентификатор пользователя и серверные права.
7. **Функциональный сценарий:** соединение двух независимых клиентов, отправка и получение контрольного сообщения, подтверждение адресата и содержимого.
8. **Устойчивость:** повторное подключение, истечение токена, потеря сети, тайм-ауты и повторная доставка — отдельными тестами.

Порядок может быть адаптирован к архитектуре компонента, но пропуск слоя должен быть объяснён и записан.

## 3. Правила локализации дефекта

Для каждой ошибки:

- зафиксировать точный failing step, ожидаемый и фактический результат;
- сохранить полный stack trace, релевантные логи, версии, конфигурацию и идентификатор CI run;
- определить последний успешно пройденный слой и первый проваленный;
- сформулировать проверяемую гипотезу и указать, какие наблюдения её подтверждают или опровергают;
- выполнить минимальный тест, который различает возможные причины;
- не делать вывод о причине по одному косвенному сообщению;
- не менять сервер, SDK, TLS и клиент одновременно «на всякий случай».

Диагностический тест обязан проверять правильный протокол, endpoint, путь и ожидаемый ответ. Ошибка самого теста (например, неверный URL path) должна быть исключена до вывода о дефекте продукта.

## 4. Минимальный набор тестов после исправления

После изменения запускается самый узкий достаточный набор:

- изменение функции — unit/component test соответствующего модуля;
- изменение сетевого клиента — тест клиента/транспорта на целевом endpoint;
- изменение TLS/сертификатов — TLS probe на том же Android API level и с тем же Network Security Config, что использует приложение;
- изменение WebSocket endpoint/proxy — Upgrade probe на точном пути, проверка статуса 101;
- изменение авторизации — отдельный тест валидного и невалидного токена;
- изменение доставки — тест отправки/получения с двумя клиентами.

Сначала выполняются быстрые локальные проверки и unit/component tests. Интеграционный тест запускается только для затронутой границы.

## 5. Когда запускать полный E2E

Полный E2E разрешён и обязателен:

- после успешного прохождения затронутых промежуточных проверок;
- перед подтверждением интеграционной готовности соответствующего сценария;
- перед релизным/приёмочным gate;
- при изменениях, затрагивающих несколько интеграционных границ, или когда дефект невозможно изолировать узким тестом.

Полный E2E не запускается автоматически после каждого изменения документации, диагностического скрипта или изолированного компонента. По умолчанию он запускается вручную/по явному решению после прохождения быстрых gates. Если CI запускает полный E2E автоматически, его триггер и причина должны быть явно задокументированы; предпочтение отдаётся отдельному ручному workflow_dispatch.

## 6. Критерии успеха и статусы

Нельзя смешивать следующие статусы:

- **Исправлено в коде** — изменение сохранено в ветке, но ещё не проверено.
- **Узкий тест пройден** — конкретный тест завершился успешно; это не означает, что пройден E2E.
- **Интеграционный тест пройден** — соответствующая интеграционная граница проверена.
- **Полный E2E пройден** — весь описанный сценарий завершился успешно, включая проверку полученного сообщения.
- **Готово к релизу** — выполнены все применимые release gates; один успешный E2E этого не доказывает.

Каждое заявление о прохождении сопровождается ссылкой на CI run/артефакт, точным тестом и его результатом. Статусы in_progress, skipped, cancelled и отсутствие лога не являются успехом.

## 7. Документирование

Для каждого исправления вести запись в журнале диагностики:

| Поле | Что фиксировать |
|---|---|
| Дата и идентификатор | дата, issue/CI run, commit |
| Симптом | точная ошибка и failing step |
| Последний успешный слой | подтверждённый факт |
| Корневая причина | доказанная причина либо [НЕ УСТАНОВЛЕНА] |
| Исправление | файлы и смысл изменения |
| Узкий тест | команда/CI step и результат |
| Регрессия | нужен ли полный E2E и почему |
| Остаточные риски | что ещё не проверено |

Не удалять историю неудачных попыток: они нужны, чтобы не повторять одни и те же проверки и гипотезы.

## 8. Экономия времени CI

- Не запускать эмулятор и полный E2E для изменений, которые можно проверить unit/component test или статической проверкой.
- Не повторять полный прогон без изменения кода/окружения/гипотезы.
- Для повторного прогона указывать, что именно изменилось с прошлого запуска.
- Разделять build/unit, transport, protocol/auth и full E2E jobs.
- Диагностические артефакты должны содержать достаточные логи, но не секреты, токены, приватные ключи или персональные данные.
- Долгие jobs должны иметь понятные timeout, диагностические этапы и cleanup через always().

## 9. Текущее применение к JuggleIM PoC

Порядок проверки: TCP → TLS с Android Network Security Config → WebSocket Upgrade на фактическом JuggleIM пути /im → SDK handshake/callbacks → авторизация → Alice/Bob message round-trip. Для WebSocket ожидается 101 Switching Protocols. Тестирование / не доказывает работоспособность или неисправность endpoint /im.

Этот раздел описывает текущий PoC. Он не утверждает, что JuggleIM уже выбран как окончательная production-архитектура.
